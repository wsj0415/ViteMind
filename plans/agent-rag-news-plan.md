# ViteMind Agent / RAG 订阅与审核执行计划

状态：规划；尚未实施。日期：2026-11-01。

## 目标与范围

以入门实践、项目复现为主，精选进阶 Agent 与 RAG 内容。每天筛选 8–12 条候选，发布最多 5 条，允许零条。审核为可配置开关：默认关闭，满足规则的候选自动发布；开启时进入待审核队列，管理员选择后批量发布。中英文不限；文章提供中文摘要和原文链接。观点最多每天发布一条；付费成本未核实时标注未知。首批关注 LangGraph、LlamaIndex、Haystack、OpenAI Cookbook、Claude Cookbooks。先支持 RSS 和 GitHub；预留 MCP、Skills、社交媒体的适配边界，不在本期实现社交平台采集。

重大发布观察过去 24 小时；教程、项目观察过去 7 天。发布日期、更新时间和首次发现时间分开保存，不能推测缺失日期。已进入队列的内容不重复推送，待审核内容持续保留。系统只提出重复建议；开启审核时由管理员确认合并及来源，关闭审核时对疑似重复的条目暂不自动合并或重复发布，留待后台处理。拒绝原因用于排序，不永久封禁来源。正文不足时须明确告知，不生成无证据的延伸分析。

## 现状与约束

- `scripts/generate_news.py` 同时负责 RSS 抓取、截取正文、模型调用和 JSON 草稿；目前候选只有前 15 条，校验仅保证返回链接属于输入、日期从候选复制，不能保证摘要事实正确。
- `.github/workflows/daily_news.yml` 每天运行并上传 14 天有效的 Artifact；草稿不会自动进入后台，未审核项不能依赖 Artifact 永久保存。
- `docs/admin/news.md` 管理 Supabase `news` 表，`docs/.vitepress/theme/components/NewsGallery.vue` 却读取 `docs/public/data/news.json`。后台改库不会自动更新首页。
- `scripts/update_rls_for_admin.sql` 是历史脚本，其 `TO authenticated USING (true)` 对所有认证用户授权；不能据此假定线上策略安全，必须通过实际项目权限和策略核实。此前 Supabase 连接器与 ViteMind 项目不属于同一个账号，不对 `hotfeed` 执行迁移。
- GitHub Pages 为静态站点；浏览器端不可存放 service role key 或 GitHub token。GitHub Actions 不能直接复用个人电脑上的 MCP、Skills 或登录态。

## 外部方案调研（2026-11-01）

| 项目 | 思路与依赖 | 决定 |
| --- | --- | --- |
| [RSSHub](https://github.com/DIYgod/RSSHub) | TypeScript、AGPL-3.0；多来源路由适配，部分社交来源可能失效或需认证 | 借鉴来源隔离和错误状态；本期不部署，不复制代码 |
| [FreshRSS](https://github.com/FreshRSS/FreshRSS) | PHP、AGPL-3.0，可使用 PostgreSQL/MySQL/SQLite；RSS 与条目状态分离 | 借鉴源管理与条目状态，以及防止内网请求的思路；不替换现有栈 |
| [Glance](https://github.com/glanceapp/glance) | Go、AGPL-3.0，多来源信息面板 | 借鉴单源独立配置和失败提示；不复制代码 |

许可证以项目仓库为准。未对上述项目做逐行代码或完整安全审计；社交平台可用性、免费额度和授权方式尚未验证，实施前重新核查。借鉴设计不等同复制代码；如需复用第三方代码，先核对许可证、来源和适配性。

## 目标架构

```text
RSS / GitHub ──┐
未来 MCP / Skill ─┼→ 连接器 → 标准化 → 原文抓取 → 去重建议 → 排序与摘要
未来社交媒体 ───┘                               ↓
                               Supabase 私有候选与审核记录
                                               ↓
                       设置：自动发布（默认） / 人工审核
                                  ↙                    ↘
                       规则校验后自动发布      后台勾选、编辑、预览
                                  ↘                    ↙
                         受保护的批量发布事务 + 发布/撤回历史
                                               ↓
                            公开的已发布视图 → 首页
```

建议将 Supabase 作为候选和公开新闻的唯一事实来源，首页读取只包含已发布内容的公开接口；静态 JSON 作为迁移期回退，不作为另一个可独立写入的主数据源。需验证恢复后的真实项目 RLS、匿名读取、缓存、可用性与限额；数据库暂不可用时显示明确错误，不能假装没有新闻。若验证表明运行时读取不可接受，则采用版本化 JSON 快照 + 发布后构建，并明确缓存和失败重试；在验证前不承诺两种方式同时作为主路径。

数据对象最小集合：settings（审核开关、屏蔽规则）、source（获取类型、配置、启用、状态）、source_run（时间、数量、脱敏错误）、candidate（稳定 ID、内容与三个时间、状态）、candidate_source（同一事件多个出处）、review_event（管理员操作及原因）、published_news（可追溯版本与撤回状态）。采集实体保留原始链接、作者、原文摘要、获取方式、正文可用程度；使用来源 ID + 来源内 ID / 规范化 URL 幂等。必须记录 unknown、部分失败及链接不可访问等状态。

## 阶段 0：基线与文档核实

1. 只读确认 ViteMind 的真实 Supabase 项目、表、数据量、Auth 设置、已部署 RLS 和当前管理员身份；禁止用不同项目 `hotfeed` 代替。读取 [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) 与当前 changelog。
2. 备份并盘点 Supabase `rss_feeds` 中原有来源及内置 `RSS_FEEDS`，记录 URL、名称、启停状态、关键词和获取方式；对比两份清单，不覆盖、不删除任何原有订阅源，无法访问的来源标记异常而非删除。确认五个来源的真实更新渠道与 API：用 [GitHub releases API](https://docs.github.com/en/rest/releases/releases#list-releases) 检查稳定 release、分页、限流；Cookbook 仓库更新不一定提供 release，需验证可获取的文章变更和日期，不伪造发布日期。
3. 梳理真实 `news`、静态 JSON 差异和历史保留策略，生成迁移备份与回滚方案。评估 GitHub Actions Secret 来源，禁止输出密钥。
4. 核对 RSSHub、FreshRSS、Glance 当前许可证、版本、依赖和开放问题；以现有 `feedparser`、`safe_get` 为基线，不因扩展性预先引入完整聚合服务。

验收：列出已确认项目、数据基线和接口证据；未获得管理员授权与数据库访问前不运行迁移。禁止以 `authenticated` 单独视为管理员；禁止凭空假设 RSS 路径和 API。

## 阶段 1：统一候选与连接器

- 在现有 Python 项目中定义小型 source adapter 契约，输出统一记录和独立运行状态；保留来源 URL 与记录关联，按 source、事件、时间精确去重。来源管理中分别显示获取方式（RSS、GitHub，预留 MCP、Skill、社交媒体）和内容类型；两者不是同一字段。迁移保持数据库原有来源 ID、名称、配置与启停状态；内置回退源单独标记为回退，不自动启用成常规源，避免改变现有采集范围。首批 5 个来源只增量添加，重复仅提示并人工确认。
- 拆分现有 RSS 流程，复用 `scripts/sentinel_safe_requests.py` 的 SSRF 防护；新增 GitHub release 连接器，限制首批已确认来源，正确处理超时、分页、限速和部分失败。
- 单独设计 GitHub Cookbook 内容变更适配方式，以实际可追溯文章为单位，不能把每次 commit 直接变新闻。
- 采集侧接受受信任本机运行器写入统一队列；本阶段只定义契约与权限，MCP/Skills 不假装已接入。[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)用于确认协议能力，不假设 Skill 可在 Actions 中运行。

验收：fixture 覆盖时间窗口、未知日期、重复、超时、不可用源、保留来源和注入内容；一次采集失败只影响该来源，全失败不得显示成“无新闻”。

## 阶段 2：质量筛选与待审核队列

- 设置中心提供审核开关，初始为关闭：关闭时，通过来源、屏蔽词、结构、链接、时效和数量规则的内容自动发布；开启时进入待审核队列。自动通过不代表事实已人工核验，不能宣称内容完全准确。设置变更记录操作者与时间；切换不追溯发布已存在的待审核内容。
- 增加可编辑屏蔽关键词：支持启用/停用、全局或按内容类型生效；默认对标题、摘要和来源摘录进行大小写不敏感的字面匹配，命中记录规则与原因并阻止发布，可在后台查看并解除屏蔽。空白词不生效；不使用不受控正则。
- 内容分类区分“技术动态”（重要发布和技术变化）、“实操教程”（有明确操作步骤或可运行示例）、“项目推荐”（值得复现的项目）、“观点分析”（非操作性分析）；系统建议分类并允许管理员修正，证据不足时标记“待分类”，不自动归入教程。来源获取方式与内容类型独立。
- 独立排序规则：Agent/RAG 相关性、实践性、来源、成本与素材完整性；不给关键词分数虚构为可信度。保留审计理由，不保证凑足 8 条。
- 来源去重先用规范化链接和稳定 ID；同一事件相似性只产生人工确认建议，不自动合并或丢弃。记录模型和规则版本及来源摘录；不让外部文本覆盖系统指令。
- 审核持久化：pending、selected、rejected、published、withdrawn；明确可撤销转换，保存拒绝原因、修改、时间和操作者。批量上限 5，观点每天不超过 1；并发重复提交须幂等。
- 模型输出先校验结构与来源链接，日期由来源记录确定；开启审核时由人工核对事实；关闭审核时仅能执行自动校验，不保证事实准确。模型失败与无合格内容分开报告。免费额度不足时保留候选并明确提示，不自动切换付费服务。

验收：测试默认自动发布、开关切换不追溯发布、开启审核不自动发布；屏蔽词大小写/中英文/分类作用域与解除屏蔽；技术动态、实操教程、项目推荐、观点分析和待分类的显示及过滤；测试队列跨天保留、重复导入幂等、合法与非法状态迁移、缺字段和不可信链接、无候选、少于 8 条；手动比对样例原文。管理员和匿名身份做 RLS 正反验证。

## 阶段 3：管理后台与发布闭环

- 沿用 `AdminLayout` 的交互框架，但只在服务端确认管理员身份和数据库权限后展示审核功能；新增审核开关、分类型关键词屏蔽、来源获取方式与内容分类管理、候选列表、原文/摘要、来源质量、费用提示、重复建议、拒绝原因、多选与发布预览。设置页明确显示当前为自动发布或人工审核。
- 通过数据库事务或经过鉴权的服务端接口批量发布；记录版本和事件，确保选中数量及当日观点上限，失败不留下部分发布。重复点击不产生重复文章。
- 首页只公开查询已发布内容；迁移时保留静态历史数据并明确去重、分页和排序。提供后台编辑、撤回、历史及恢复，绝不依赖隐藏按钮保障权限。
- 面对 Supabase 不可用、抓取部分失败、空列表或没有合格内容，显示不同提示。原有 RSS 管理与新闻内容不被删除。

验收：迁移前后旧来源数量、URL、启停状态和关键词逐项一致；RSS / GitHub 获取方式可筛选，预留类型不能误报已接通。匿名不可读取或更改设置和屏蔽词，非管理员不可更改来源或审核开关。匿名可读已发布而不可读草稿，非管理员不可写，管理员可审核；中断/重复提交、并发、编辑、撤回和失败回滚可重复测试。桌面与手机完成一次真实浏览器审核，核对首页刷新结果与数据库一致。

## 阶段 4：运行、验证和交付

- 小批量在独立测试环境运行一次完整链路；保留旧工作流和快照直到回滚验证完成。确认调度使用 Asia/Shanghai 08:00 对应 UTC 时间，不重复发布。
- 运行现有 Python 单元测试、连接器和状态迁移测试、权限测试、`npm run docs:build`；验证 Actions 来源级状态和脱敏日志。
- 测量连续 7 日候选量、审核率、重复率、无依据错误和单次用时；再决定是否调整来源和评分。输出模型对比样本与成本，未经实测不切换模型。
- 实施独立分支/提交，提供迁移、备份、回滚及管理员操作说明。生产数据库变更前确认目标项目、备份和迁移范围；密钥不进入仓库、浏览器或日志。

## 完成标准

可在手机或桌面后台设置自动发布（默认）或人工审核，按内容类型配置屏蔽词，并按获取方式查看来源；原有来源完整保留。系统每日筛选目标 8–12 条候选（不足时不补足），自动或经管理员选择后发布 0–5 条；首页呈现完全一致，编辑和撤回可追溯。已审核条目不会重复推送；单源失败清楚可见；无合格信息可不发布。测试和浏览器验证通过，已有工具、新闻数据保留。本期不承诺社交媒体、MCP、Skills 已接通，也不承诺 AI 摘要零错误。
